# 콘텐츠 작성 지침

이 지침은 `src/content/` 아래에 작성되는 공개 콘텐츠에 적용한다.

기술 글은 홍보 글, 교과서식 튜토리얼, 감상문이 아니라 실제 문제와 판단 과정을 남기는 엔지니어링 기록으로 작성한다.

## 지침 적용 원칙

- 이 지침은 글의 표현을 획일화하기 위한 템플릿이 아니다.
- 글의 구조와 분량은 실제 내용에 따라 결정한다.
- 규칙을 지키기 위해 불필요한 문장, 소제목, 목록, 결론을 추가하지 않는다.
- 기존 작성자의 자연스러운 표현은 명확한 문제가 없는 한 유지한다.
- 모든 기술 글을 동일한 `문제 → 분석 → 해결 → 결과` 구조로 강제하지 않는다.

## 사실성

- 저장소의 코드, 사용자가 제공한 자료, 확인 가능한 프로젝트 기록을 근거로 작성한다.
- 확인되지 않은 사실, 동기, 원인, 설계 의도, 성능 개선, 운영 결과를 추측해서 작성하지 않는다.
- 실제 측정값이 없다면 벤치마크나 수치를 만들어내지 않는다.
- 검증되지 않은 결과를 `개선했다`, `해결했다`, `효과가 있었다`처럼 확정적으로 표현하지 않는다.
- 기술 선택의 이유가 자료에 나타나 있지 않다면 그럴듯한 이유를 임의로 만들어내지 않는다.
- 필요한 경우 관찰된 사실, 가설, 결정 사항, 검증되지 않은 기대 효과를 구분해서 서술한다.
- 필요한 사실이나 근거가 부족하면 그럴듯한 내용을 만들어 빈칸을 채우지 않는다.
- 정확한 서술에 필요한 정보가 없다면 해당 내용을 생략하거나 사용자에게 확인한다.

## 공개 범위와 민감 정보

- 공개 저장소에 적합한 정보만 콘텐츠에 포함한다.
- 비밀번호, token, API key, secret, 실제 IP, 계정 ID, 내부 domain, 고객 정보 등 민감하거나 식별 가능한 정보를 작성하지 않는다.
- 회사, 서비스, 고객, 내부 infrastructure를 특정할 필요가 없다면 일반화한다.
- 사용자가 제공한 운영 자료를 그대로 공개 가능한 정보라고 가정하지 않는다.
- 공개 여부가 불확실한 정보는 임의로 포함하지 않는다.
- 기술적 설명에 필요하지 않은 실제 resource name, hostname, endpoint, account identifier는 예시나 일반화된 표현으로 대체한다.
- 익명화 과정에서 기술적 의미가 달라지지 않도록 한다.

## 기존 콘텐츠 수정 범위

- 새로운 작성 지침을 기존 콘텐츠 전체에 소급 적용하지 않는다.
- 요청받은 글이나 이번 작업에서 직접 수정하는 부분에만 지침을 적용한다.
- 별도 요청 없이 기존 글의 문체, 구조, 제목을 일괄적으로 정리하지 않는다.
- 단순한 표현 선호 차이만으로 기존 문장을 다시 작성하지 않는다.
- 기존 글을 수정할 때 원래 글의 기술적 의도와 작성자의 표현을 가능한 한 유지한다.

## 기술 용어

- 개발 실무와 공식 문서에서 통용되는 표준 영문 기술 용어를 직접 사용한다.
- 자연스럽게 사용되는 영문 기술 용어를 억지로 한글로 번역하지 않는다.
- 한글 번역어 뒤에 영문을 반복하는 `용어(Term)` 형태를 지양한다.
- 영문 기술 용어 뒤의 조사는 한국어 문장 흐름에 맞게 자연스럽게 연결한다.
- 기술 용어를 더 전문적으로 보이게 만들기 위해 불필요하게 어려운 표현으로 바꾸지 않는다.

## 문체

- 담백하고 건조한 엔지니어링 톤을 유지한다.
- 문제, 제약 조건, 구현 방식, 기술 선택의 근거, 트레이드오프, 검증 결과를 중심으로 작성한다.
- 글의 내용을 이해하는 데 필요하지 않은 기초 개념을 교과서처럼 길게 설명하지 않는다.
- 주관적인 자평, 감상, 훈화성 문장을 넣지 않는다.
- 기술적 내용 없이 글을 마무리하기 위한 결론이나 교훈을 억지로 추가하지 않는다.
- 이미 설명한 내용을 결론에서 다시 길게 반복하지 않는다.
- 과장하거나 극적인 서사를 만들지 않는다.
- 실제보다 문제가 심각했거나 해결 과정이 극적이었던 것처럼 표현하지 않는다.

다음과 같은 표현은 지양한다.

- `중요성을 확인했다`
- `의미 있는 경험이었다`
- `좋은 선택이었다`
- `많은 것을 배웠다`
- `이를 통해 알 수 있었다`
- `더 나은 방향으로 발전시킬 수 있었다`

## AI 특유의 문장 패턴

- `이 글에서는`, `살펴보자`, `알아보자`, `정리하면`, `결론적으로` 같은 형식적인 도입과 전환을 반복하지 않는다.
- `핵심은`, `중요한 것은`, `단순하다` 같은 강조 표현을 습관적으로 사용하지 않는다.
- 내용을 억지로 3개 항목이나 대칭적인 구조로 맞추지 않는다.
- 서로 비슷한 길이와 구조의 문장을 반복적으로 나열하지 않는다.
- 모든 문단 끝에 요약 문장을 붙이지 않는다.
- 같은 내용을 일반 문장, 목록, 소제목, 결론에서 반복하지 않는다.
- 기술 내용이 자연스럽게 이어진다면 별도의 서론 없이 바로 문제부터 시작해도 된다.
- 마지막 기술 내용에서 글이 충분히 끝난다면 별도의 결론을 만들지 않는다.
- 독자에게 말을 거는 형식이나 불필요한 rhetorical question을 남발하지 않는다.
- 실제 내용보다 글의 구조가 지나치게 정돈되고 대칭적으로 보이도록 만들지 않는다.

## 소제목

- 다루는 기술적 내용이 바로 드러나는 간결한 명사형 구문을 사용한다.
- `~했다`, `~한다` 형태의 서술형 소제목을 지양한다.
- 감성적이거나 홍보 문구처럼 보이는 소제목을 사용하지 않는다.
- 모든 문단에 소제목을 붙이지 않고 내용상 구분이 필요한 경우에만 사용한다.
- 소제목만 읽어도 글에서 다루는 기술적 흐름을 파악할 수 있도록 한다.

권장 예시:

- `DB 연결 수와 네트워크 송신량`
- `Polling API 분리`
- `Docker JSON 로그 회전 정책`
- `Winged-Edge 연결 구조`

지양 예시:

- `문제의 원인을 찾아보았다`
- `더 나은 구조를 만들었다`
- `결국 중요한 것은 운영이었다`
- `왜 이런 문제가 발생했을까?`

## 문단과 목록

- 자연스럽게 설명할 수 있는 내용은 일반 문단을 우선한다.
- 가독성을 이유로 모든 내용을 bullet list로 바꾸지 않는다.
- 실제로 병렬적인 항목을 나열할 필요가 있을 때만 목록을 사용한다.
- 여러 항목을 직접 비교할 필요가 있을 때만 표를 사용한다.
- 동일한 내용을 일반 문장과 목록으로 중복해서 작성하지 않는다.
- 두세 문장으로 설명할 수 있는 내용을 불필요하게 여러 단계의 목록으로 분해하지 않는다.

## 코드

- 기술 내용을 설명하는 데 필요한 코드, 설정, 명령, interface만 포함한다.
- 전체 소스를 그대로 덤프하기보다 핵심 부분만 발췌한다.
- 코드만 봐도 의미가 명확한 내용을 줄 단위로 다시 설명하지 않는다.
- 공개해도 문제가 없는 경우 실제 기술적으로 의미 있는 identifier를 유지한다.
- 예제 코드를 작성해야 한다면 실제 프로젝트 코드인 것처럼 꾸미지 않고 예시임을 명확히 한다.
- 존재하지 않는 API, option, configuration을 그럴듯하게 만들어내지 않는다.

## Frontmatter

- `title`은 글에서 다루는 기술적 주제를 구체적으로 표현한다.
- `description`은 글의 내용을 직접 설명하는 간결한 기술 요약으로 작성한다.
- 일반적으로 1~2문장을 넘기지 않는다.
- 과장되거나 홍보성인 표현을 사용하지 않는다.
- 본문에서 확인되지 않은 성과나 결과를 metadata에 작성하지 않는다.
- 검색 노출을 위해 같은 keyword를 부자연스럽게 반복하지 않는다.

## 표기 규칙

- 문장 구분을 목적으로 middle-dot 계열 문자 `·`, `•`, `ㆍ`, `・`를 사용하지 않는다.
- 쉼표, 조사, 접속사 또는 별도의 문장으로 자연스럽게 연결한다.
- 굵은 글씨를 과도하게 사용하지 않는다.
- 한 문단에서 여러 표현을 연속해서 강조하지 않는다.
- 괄호 안에 부연 설명을 연속해서 붙이지 않는다.
- 별도의 요청이 없다면 기술 글에 장식용 emoji를 사용하지 않는다.
- 의미 없는 따옴표나 강조용 quotation mark를 반복해서 사용하지 않는다.

## 최종 검토

콘텐츠 작성이 끝나면 다음을 확인한다.

- 근거 없이 만들어낸 내용이 없는가.
- 확인되지 않은 결과를 확정적으로 표현하지 않았는가.
- 공개하면 안 되는 정보나 식별 가능한 정보가 포함되지 않았는가.
- 불필요한 서론이나 결론이 없는가.
- 같은 내용을 반복해서 설명하지 않았는가.
- 기본 개념을 필요 이상으로 길게 설명하지 않았는가.
- 소제목이 행동이나 감상이 아니라 기술적 내용을 나타내는가.
- 불필요한 목록이나 표를 만들지 않았는가.
- 실제 내용보다 지나치게 깔끔한 서사나 인위적인 구조를 만들지 않았는가.
- 기존 글을 요청 범위 이상으로 다시 작성하지 않았는가.
- AI가 작성한 일반적인 설명문보다 실제 엔지니어링 기록처럼 읽히는가.
