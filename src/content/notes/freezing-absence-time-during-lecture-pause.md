실시간 교육 모니터링 화면에서 수업을 쉬는 시간으로 전환해도 학생의 이탈 시간이 계속 늘었다. 학생 화면에서는 감지와 상태 전송이 일부 이어졌고 관리자 화면은 늦게 도착한 상태 메시지나 Redis에 남은 진행 중 구간을 반영했다. 수업을 재개하면 이전 메시지가 누적값을 덮어써 횟수와 시간이 줄어드는 경우도 있었다.

여기서 이탈 시간은 학생이 자리를 비운 것으로 감지된 구간의 누적 시간이다. 수업 전체의 경과 시간과는 다르다. 쉬는 시간 직전까지의 기록은 남기되, 쉬는 시간 동안에는 이탈과 졸음을 집계하지 않아야 했다.

## 수업 참여와 감지 실행 조건

학생 화면에는 수업에 참여할 수 있는지를 나타내는 조건이 있었다. 수업 진행 중뿐 아니라 일시정지 상태에서도 참이었다. 쉬는 시간이 끝나면 기존 카메라로 다시 참여해야 하므로, 일시정지를 참여 종료와 같게 취급할 수는 없었다.

반면 감지와 상태 전송은 수업이 실제로 진행 중일 때만 실행해야 했다. 기존 STATUS heartbeat는 카메라 실행 상태를 확인했지만, 수업이 일시정지됐는지를 조건에 포함하지 않았다. 카메라를 유지한 채 쉬는 시간에 들어가면 5초 주기의 전송이 계속될 수 있는 구조였다.

참여 가능 여부는 유지하고, 감지를 실행할 수 있는 조건을 따로 뒀다. PAUSE를 받으면 감지 worker와 STATUS heartbeat, 로그 타이머, 알림 타이머를 멈췄다. 상태 메시지를 실제로 보내는 함수에서도 감지 실행 여부를 확인하도록 했다. WebSocket 재연결 직후의 상태 재전송에도 같은 조건을 적용했다.

카메라 스트림과 WebSocket 연결은 유지했다. RESUME을 받으면 기존 스트림으로 감지를 재개한다. 학생 화면에는 이전 감지 결과나 카메라OFF보다 쉬는시간 표시를 우선했다.

## 진행 중 구간의 마감

이탈 시간 계산에는 완료된 구간의 누적값과 진행 중 구간의 시작 시각이 함께 쓰였다. 동작을 단순화하면 다음과 같다.

```text
진행 중 구간이 없을 때: 완료된 구간의 누적 시간
진행 중 구간이 있을 때: 완료된 구간의 누적 시간 + 현재 시각 - 구간 시작 시각
```

시작 시각을 남겨두면 새 상태 메시지가 없어도 조회 시점에 따라 계산 결과가 커진다. 관리자 화면에서 타이머를 멈춰도 Redis에 열린 구간이 남아 있으면 새로고침 뒤 REST로 상태를 복원하면서 쉬는 시간이 다시 포함될 수 있었다.

진행 중 구간을 PAUSE 시점까지만 집계해 마감해야 했다. 학생 화면은 열려 있던 이탈과 졸음 구간을 마감해 로그를 보내고 시작 시각을 비웠다. 백엔드에서도 PAUSE 처리에 Redis 구간 마감을 추가했다. 마감 시각까지의 시간을 누적값에 더하고 횟수를 반영한 뒤, 진행 중 구간의 시작 시각을 제거했다.

이미 마감된 레코드를 다시 처리할 때는 더할 구간이 없어야 한다. 시작 시각이 없는 레코드는 횟수와 시간을 그대로 유지하도록 했다. 동일 레코드를 두 번 마감해도 누적값이 늘지 않는지는 별도 테스트로 확인했다.

이렇게 마감한 구간은 쉬는 시간 동안 길어지지 않는다. 재개 후 다시 이탈을 감지하면 새 구간으로 집계한다. 학생 화면과 서버는 각각 PAUSE를 처리하는 시각에 마감하므로, 이 수정만으로 두 시각이 정확히 같아지는 것은 아니다.

## 관리자 화면의 상태 반영

학생 화면에서 전송을 멈추더라도 이미 보낸 STATUS가 늦게 도착할 수 있다. 기존 관리자 수신 조건은 수업 진행 중과 일시정지 상태를 모두 허용했다. 이를 진행 중일 때만 반영하도록 바꿨다. 수업 재개 이벤트와 학생 입퇴장 메시지는 계속 처리했다.

표의 시간 계산도 수정했다. 일시정지 상태에서는 진행 중 구간을 더하는 계산에 들어가기 전에 누적값을 반환하도록 했다. 감지 상태와 참여 상태는 `—`로 표시했다. 수업이 멈춰 있는 동안에는 마지막 감지 결과를 현재 상태처럼 보여주지 않도록 한 것이다.

재개 시에는 오래된 WebSocket 값이 로컬 누적값을 덮어쓰는 경로를 수정했다. 메시지의 값과 로컬에 보관한 값 중 큰 값을 남겨 이미 마감한 횟수와 시간이 작은 값으로 돌아가지 않도록 했다.

이 비교는 같은 집계 범위의 누적값을 보존하는 처리다. 새 수업을 시작할 때는 추적 상태를 초기화하고, 쉬는 시간에서 재개할 때는 유지했다. 감소할 수 있는 일반적인 상태값까지 최댓값으로 합치는 규칙으로 쓸 수는 없다.

## PAUSE 이후 도착한 폴링 응답

후속 수정에서는 학생 세션 폴링도 다뤘다. 학생 화면은 WebSocket 이벤트 외에 5초 주기 폴링으로 수업 상태를 확인했다. 그런데 PAUSE 전에 시작한 요청이 나중에 진행 중 응답을 반환하면, 이미 멈춘 감지가 다시 시작될 수 있었다.

```text
세션 조회 요청 시작
→ PAUSE 이벤트 수신, 감지 중지
→ 이전 요청의 진행 중 응답 도착
→ 화면이 다시 감지 상태로 전환
```

요청 이후에 세션 이벤트를 받았는지를 확인하도록 generation 값을 추가했다. START, RESUME, PAUSE, END를 받을 때마다 값을 올리고 폴링 요청 시작 시의 값과 응답 도착 시의 값이 다르면 그 응답을 적용하지 않았다.

같은 PAUSE가 다시 들어와 상태 이름이 그대로여도 generation은 바뀐다. 요청 전후 상태 이름만 비교하면 놓칠 수 있는 이벤트 수신을 구분하려는 처리다. 이벤트를 놓친 경우에는 기존 폴링 응답으로 상태를 복구하는 동작을 유지했다.

이 값은 학생 화면 안에서 수신한 이벤트의 순서를 추적한다. 서버가 발급한 버전이나 메시지의 생성 시각은 아니므로, 네트워크 전체의 메시지 순서를 보장하지는 않는다.

## 회귀 테스트와 확인 범위

관리자 누적 계산 테스트에서는 진행 중 이탈 구간을 10초에서 마감한 뒤 시간을 더 진행시켜도 표시값이 10초로 유지되는지 확인했다. 재개 후 새 구간이 5초 이어지면 기존 10초에 더해 15초가 되는지도 검사했다.

백엔드 테스트는 이탈과 졸음 구간을 마감한 레코드에서 시작 시각이 사라지는지, 나중 시각으로 총 시간을 조회해도 값이 유지되는지, 반복 마감 시 횟수와 시간이 그대로인지 다룬다. 마감된 레코드를 Redis에 쓰는 경로도 mock으로 확인했다.

학생 화면 테스트에는 일시정지 중 감지 비활성화와 쉬는시간 표시, PAUSE와 END 뒤에 도착한 오래된 폴링 응답 무시, 중복 이벤트 수신, 누락된 START의 폴링 복구를 포함했다. 글을 정리하면서 관련 프론트 테스트 4개 파일의 13개 테스트를 다시 실행했고 모두 통과했다.

실제 카메라를 켜고 이탈 상태에서 PAUSE한 뒤 대기, 새로고침, RESUME을 거쳐 DB 기록까지 확인하는 절차는 당시 PR에 dev 검증 시나리오로 남아 있다. 이번 글 작성 중에는 해당 시나리오를 다시 실행하지 않았다. 위 결과는 코드와 회귀 테스트에서 확인한 범위다.
