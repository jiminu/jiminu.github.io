관리 서비스의 스키마와 권한 데이터 변경은 개발 환경과 운영 환경, 테넌트 DB마다 SQL을 수동으로 실행하고 있었다. 별도의 신청 서비스도 같은 DB를 사용했고, 변경 이력이 두 저장소에 흩어져 있었다. 같은 변경을 어느 DB에 적용했는지와 앞으로 어느 저장소에서 관리할지를 함께 정리해야 했다.

관리 서비스에 Flyway를 도입하면서 스키마와 권한 데이터 변경을 한 저장소의 migration으로 모았다. 신청 서비스가 사용하는 컬럼도 같은 경로에서 변경하도록 했다. 여기서는 테넌트 이름을 A, B, C로 바꾸어 설명한다.

## 기존 DB와 빈 DB의 기준선

테넌트마다 현재 스키마가 달라 V1 파일도 따로 준비했다. 이 파일은 빈 DB를 구성할 때 실행할 기준선이다. 이미 운영 중인 DB에서 같은 DDL을 다시 실행하는 용도는 아니다.

기존 DB에는 버전 1을 기준선으로 기록하고 이후 migration부터 적용하도록 설정했다. 설정의 관련 부분만 옮기면 다음과 같다.

```java
.baselineOnMigrate(true)
.baselineVersion("1")
```

Flyway 이력 테이블이 없는 비어 있지 않은 스키마에서는 baseline을 기록한 뒤 그보다 높은 버전만 적용한다. 빈 DB에서는 V1 migration을 실행해 스키마를 만든다. [baselineOnMigrate 공식 문서](https://documentation.red-gate.com/fd/flyway-baseline-on-migrate-setting-277578974.html)

baseline을 기록하는 것과 기존 스키마가 V1과 같은지 검사하는 것은 별개다. 이 옵션만으로 수동 변경이 남아 있는지 확인할 수는 없다. 도입 당시에는 로컬 MySQL에서 빈 DB와 운영 스키마 복사본을 나누어 확인했다. 검증 기록에는 빈 DB의 V1 실행 후 스키마가 운영과 일치했고, 운영 스키마 복사본에서는 버전 1의 baseline만 기록되며 migration 실행은 0건이었다고 남아 있다.

## 공통 변경과 테넌트별 변경

모든 테넌트에 적용할 변경과 특정 테넌트에만 적용할 변경을 폴더로 나눴다. 아래 구조에서 테넌트 이름은 설명용이다.

```text
db/migration/
  common/
  tenant-a/V1__baseline.sql
  tenant-b/V1__baseline.sql
  tenant-c/V1__baseline.sql
```

각 DB에는 `common`과 해당 테넌트 폴더를 함께 지정한다. A의 migration을 실행할 때 B와 C의 V1 파일은 읽지 않는다.

공통 폴더와 테넌트 폴더는 실행할 때 합쳐지므로 버전 번호가 겹치면 안 된다. 테넌트별 V1은 서로 다른 DB에서 실행되므로 허용하지만, 공통 V1을 추가하면 각 테넌트의 V1과 충돌한다. 이후 새 번호는 모든 폴더의 최댓값에 1을 더하는 규칙으로 정했다.

폴더 구성 테스트는 파일 이름 형식, 각 테넌트의 V1 존재 여부, 공통 폴더와 해당 테넌트 폴더를 합쳤을 때의 버전 중복을 검사한다. 이 테스트는 SQL 자체를 실행하지 않는다. 도입 당시 공통 폴더에 V1을 추가했을 때 세 테넌트의 구성 테스트가 모두 실패하는지도 확인했다.

## 테넌트 DataSource별 실행

애플리케이션은 요청에 따라 DB를 선택하는 routing DataSource를 사용한다. 기본 DataSource에만 migration이 실행되도록 두면 각 테넌트 DB의 변경을 처리할 수 없다.

Spring Boot의 Flyway 자동 실행은 끄고, 테넌트별 연결 풀을 만든 직후 각 DataSource를 지정해 `migrate()`를 호출했다. 기본 연결과 한 테넌트 연결은 같은 DB를 가리키므로 중복 실행 대상에서 제외했다.

![관리 서비스가 공통 폴더와 해당 테넌트 폴더를 조합해 A, B, C DB에 각각 migration을 실행하는 구조](/images/adopting-flyway-for-existing-tenant-databases/tenant-migration-flow.svg)

migration이 실패하면 예외를 전파해 애플리케이션 기동을 중단한다. 다만 여러 테넌트의 변경이 하나의 트랜잭션으로 묶이는 구조는 아니다. 앞선 테넌트에 적용된 변경이 뒤의 실패로 함께 취소되는 것은 아니므로, 기동 실패와 전체 DB의 원상 복구를 같은 의미로 볼 수는 없다.

로컬 설정은 개발 DB에 연결할 수 있어 migration 실행을 별도 옵션으로 껐다. 로컬 DB에서 확인할 때만 켜도록 했다. H2 기반 애플리케이션 테스트에서도 자동 실행을 껐기 때문에, 해당 테스트 통과를 MySQL migration 실행 검증으로 해석하지 않았다.

## 같은 DB를 사용하는 두 서비스의 배포 순서

migration 파일을 한곳으로 모아도 DB를 사용하는 서비스는 둘이었다. 관리 서비스에서 스키마를 바꾸는 동안 기존 신청 서비스가 계속 같은 테이블에 쓸 수 있어야 했다.

컬럼 추가는 NULL을 허용하거나 기본값을 두고, migration을 소유한 관리 서비스를 먼저 배포한 뒤 신청 서비스를 배포하도록 정했다. 컬럼 삭제나 이름 변경은 두 서비스의 코드가 기존 컬럼을 사용하지 않도록 먼저 배포하고, 다음 릴리즈에서 진행하도록 했다.

이미 배포한 migration 파일을 고치는 대신 새 버전을 추가하고, 권한 데이터 추가도 존재 여부를 확인하는 SQL로 작성하도록 규칙을 남겼다. 기존 수동 SQL은 과거 변경 기록임을 표시했다.

도입 당시 검증 기록에는 Gradle 테스트 191개 중 1개 skip과 나머지 통과, 로컬 MySQL 8.4에서 빈 DB와 기존 스키마 복사본을 사용한 확인이 남아 있다. 당시 사용한 Flyway 8.5.13은 MySQL 8.4가 지원 범위보다 새롭다는 경고를 출력했으므로, 이 확인을 공식 지원 범위나 모든 migration의 호환성 보장으로 확대하지 않는다. 이 글을 작성하면서 운영 DB에 migration을 다시 실행하지는 않았다.
