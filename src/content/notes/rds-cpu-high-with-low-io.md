운영 RDS CPU가 수업 시간마다 100%에 도달했다. 처음 떠오른 원인은 실시간 상태 데이터의 대량 저장이었다. 카메라에서 감지한 상태가 짧은 주기로 들어오고 있었으니 자연스러운 의심이었다.

하지만 지표를 나란히 놓자 다른 그림이 보였다. CPU는 포화됐지만 Read IOPS와 Write IOPS는 낮았고 디스크 지연도 안정적이었다. 반면 DB 연결 수와 네트워크 송신량은 수업 시간에 함께 증가했다.

CPU 그래프만 보고 인스턴스를 키우기 전에, 어떤 작업이 CPU를 사용하고 있는지 다시 좁혀야 했다.

## 비교 기준

하루의 최댓값 하나만 보면 수업 규모나 시간을 알 수 없다. 배포 전후를 비교하려면 조건을 함께 남겨야 한다.

- 같은 기능이 사용되는 시간 구간
- 비슷한 동시 접속자 수
- 측정 시작과 종료 시각
- CloudWatch period와 통계 방식
- 배포 커밋과 애플리케이션 버전

최근 일주일을 10분 단위로 조회하고 날짜별 평균과 최댓값을 계산했다. 평일에는 CPU 최대 100%가 반복됐지만, 기능 사용이 적은 주말에는 한 자릿수였다. 애플리케이션 트래픽과 직접 연결된 패턴이었다.

## 낮은 IOPS와 latency

측정 구간에서 Read IOPS는 초당 1회보다 훨씬 낮았고 Write IOPS도 한 자릿수였다. 읽기와 쓰기 latency, 여유 메모리, 저장공간도 안정적이었다.

이 결과만으로 디스크 병목이 절대 아니라고 확정할 수는 없다. 그러나 "실시간 데이터가 너무 많이 저장돼서 CPU가 올랐다"는 첫 가설의 우선순위는 낮출 수 있었다.

대신 다음 지표가 눈에 띄었다.

- 복수의 애플리케이션 인스턴스가 사용하는 DB 연결 수가 동시에 증가했다.
- CPU 최고 구간에 연결 수가 평소보다 많았다.
- DB에서 애플리케이션으로 나가는 네트워크 송신량이 비업무일보다 크게 증가했다.

쓰기보다 반복 조회와 큰 결과 반환을 먼저 의심할 근거였다.

## Polling API의 조회 범위

클라이언트는 현재 세션이 열려 있는지만 확인하면 됐다. 하지만 주기적으로 호출하던 API는 당일 상태 로그를 모두 조회한 뒤 애플리케이션에서 누적 통계를 계산했다.

관리자 통계 화면에는 필요한 API였지만 학생 화면의 상태 확인에는 과한 계약이었다. 동시 접속자가 늘면 같은 종류의 조회와 결과 전송이 반복됐다. WebSocket 이벤트를 이미 받고 있어도 새로고침과 이벤트 누락 복구를 위해 폴링은 계속 실행되고 있었다.

문제는 폴링 자체보다 폴링이 호출하는 API의 비용이었다.

## Polling API와 집계 경로 분리

최적화 목표는 실시간 기능을 없애는 것이 아니었다. 화면과 복구 동작은 유지하면서 요청마다 수행하는 일을 줄였다.

1. 현재 열린 세션 한 건만 반환하는 경량 API를 추가했다.
2. 학생의 상태 확인 폴링만 경량 API로 전환했다.
3. 관리자 통계 API는 유지하되 전체 엔티티를 읽어 애플리케이션에서 계산하던 부분을 SQL 집계로 바꿨다.
4. WebSocket은 즉시 상태 변경을 전달하고, 경량 폴링은 새로고침과 재연결 복구의 안전망으로 남겼다.
5. 기존 API를 제거하지 않아 문제가 생기면 클라이언트만 되돌릴 수 있게 했다.

실시간 이벤트를 공유하던 Redis Pub/Sub도 유지했다. 여러 WebSocket 서버에 나뉘어 연결된 사용자에게 같은 이벤트를 전달하려면 공용 fan-out 경로가 필요하다. 줄여야 했던 것은 Pub/Sub 자체가 아니라 이벤트마다 뒤따르던 불필요한 조회, Redis 왕복과 상세 로그였다.

## 로그 경로와 RDS 부하 분리

같은 시기에 애플리케이션 로그가 컨테이너 쓰기 레이어를 채우며 서버 CPU까지 높인 사건이 있었다. RDS CPU 문제와 시간상 겹쳤지만 원인과 대응은 구분해야 했다.

애플리케이션 파일 로그, Docker JSON 로그, systemd journal은 서로 다른 경로에 쌓인다. 한 곳의 보존 정책만으로 나머지가 제한되지는 않는다. 각 경로에 기간과 총량 상한을 두고, 컨테이너 파일 로그는 명시적인 호스트 경로에 마운트하도록 배포 구성을 바꿨다.

로그 보존 정책의 구체적인 진단 명령과 경로별 상한은 이 글의 범위에서 제외하고, RDS 지표와 애플리케이션 호출 경로의 관계에만 집중했다.

## 운영 전후 관측

코드가 효율적으로 보인다는 것과 운영 부하가 실제로 감소했다는 것은 다르다. 그래서 변경 전과
변경 후의 같은 길이 구간을 CloudWatch로 비교했다. CPU 포화는 재현되지 않았고 DB 연결 수와
네트워크 송신량도 낮아졌다. Write IOPS와 평균 latency가 모두 같은 방향으로 변한 것은 아니었지만,
관측된 latency와 메모리, 저장공간에서 스토리지 압박을 가리키는 징후는 없었다.

![RDS CPUUtilization 2주 추이 그래프](/images/rds-cpu-high-with-low-io/rds-cpu-utilization.png)

2주 CloudWatch CPUUtilization에서 앞 구간에는 CPU 포화가 반복됐고, 뒤 구간에는 같은 형태의
포화가 보이지 않았다. 이 그래프는 기간 전체의 반복 패턴을 보조적으로 보여주며, 아래 표의 15개
datapoint 비교를 대체하지 않는다.

| RDS 지표 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| CPU 평균 | 99.49% | 5.25% |
| CPU 최대 | 100% | 7.48% |
| DB 연결 수 평균 / 최대 | 62.09 / 64 | 20.27 / 22 |
| 네트워크 송신 평균 / 최대 | 487.5 / 799.5KiB/s | 29.3 / 37.6KiB/s |
| Read IOPS 평균 / 최대 | 0.29 / 2.47/s | 0.28 / 2.47/s |
| Write IOPS 평균 / 최대 | 5.49 / 9.27/s | 6.56 / 8.80/s |
| Read latency 평균 / 최대 | 0.10 / 0.80ms | 0.24 / 4.00ms |
| Write latency 평균 / 최대 | 0.38 / 1.10ms | 0.70 / 1.02ms |

각 구간은 5분 CloudWatch datapoint 15개로 구성했다. 평균은 `Average`의 산술평균이고, 최대는
`Maximum` 중 최댓값이다.

이 관측은 원인 하나를 증명하지 않는다. 경량 API, SQL 집계, Redis 호출 축소, 인덱스 등 여러 변경이
가까운 시기에 함께 반영됐고, 과정, 참여 인원, 수업 상태 전환 시각도 두 구간에서 감사 가능하게
기록되지는 않았다. 따라서 여기서 확인한 것은 **같은 길이의 수업 시간대에서 고부하가 재현되지
않은 1차 관측**이며, 각 변경의 단독 기여율은 아니다.
